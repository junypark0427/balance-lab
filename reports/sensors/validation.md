# 손목 컨트롤러 연동 검증

기록일: 2026-10-26~2026-10-27, Asia/Seoul. Godot 4.7.2 / Jolt / macOS Metal / ESP32 코어 3.3.12.
실제 사용자와 손목 방향을 맞추며 검증 중입니다. 합성 입력 검사를 실제 센서 플레이와 구분합니다.

## 하드웨어와 기존 배선 확인

esptool에서 두 장치 모두 ESP32-D0WD-V3 revision 3.1, 40MHz로 식별했습니다.
이는 칩 정보이며 제조사별 개발보드 PCB 모델이나 외관의 WROOM 모듈 품번을 독립 확인한 것은 아닙니다.
사용자는 한 대를 ESP32, 다른 한 대를 ESP32-WROOM으로 설명했습니다.
USB VID/PID는 모두 1a86:7523이고 USB serial number는 비어 있으므로 포트 순서로 역할을 정하지 않습니다.

| MAC 기반 ID | 최초 관측 포트 | 검증한 I²C |
| --- | --- | --- |
| esp32-680947606060 | /dev/cu.usbserial-110 | SDA GPIO21, SCL GPIO22 |
| esp32-08d1f9e7279c | /dev/cu.usbserial-10 | SDA GPIO21, SCL GPIO22 |

두 장치의 기존 펌웨어를 각각 리셋한 뒤 다음 실제 출력과 가속도 측정값을 받았습니다.

```text
ESP32 MPU6050 quick test | SDA=21 SCL=22
Probe 0x68: status=0
WHO_AM_I: 0x68
MPU6050 FOUND: 0x68
```

현재 배선은 바꾸지 않았습니다. D2/D3를 GPIO2/GPIO3으로 추정하지 않았고, 현재 ESP32와 다른
과거 Pro Micro 5V 기록 및 원래 하드웨어 시험 스케치 3개도 그대로 보존했습니다.

## 새 펌웨어와 동시 수신

[펌웨어](../../hardware/controller_firmware/controller_firmware.ino)를 esp32:esp32:esp32,
BALANCE_SDA=21, BALANCE_SCL=22로 빌드했습니다. Flash 306,212 bytes, RAM 23,732 bytes입니다.
한 대씩 115200 baud로 업로드해 두 기기 모두 기록 데이터 해시 검증에 성공했습니다.
근거: [업로드 A](upload-a.log), [업로드 B](upload-b.log).

새 펌웨어의 서로 다른 MAC ID, Roll/Pitch, 가속도·자이로를 두 USB 포트에서 동시에 수신했습니다.
센서 초기화/설정 readback/읽기가 실패하면 정상값 대신 오류 프레임을 보냅니다.
시리얼 포트 경로는 설정에 고정하지 않으며 운영체제 포트 탐색을 사용합니다.

조사 중 빠른 속도의 flash 읽기에서 패킷 오류가 발생했고, 115200 전체 flash 백업도 긴 읽기 중
손상 오류로 실패했습니다. 전체 flash 백업이 완성됐다고 보고하지 않습니다.
실제 업로드는 한 대씩 115200으로 수행해 해시 검증을 통과했습니다. 원래 시험 스케치는 보존되어 있습니다.

## 사용자 동작으로 역할과 축 맞추기

처음 P1만 좌우로 움직이는 구간에서 680947606060 장치의 Pitch 변화는 약 39.39도,
Roll 변화는 약 28.34도였고 다른 장치의 Pitch 변화는 약 0.12도였습니다.
P1은 해당 ID, P2는 나머지 ID로 지정했습니다. 역할은 로컬 설정에 저장합니다.

첫 P2 앞뒤 동작 기록에서 Pitch 변화가 약 18.23도, Roll 변화가 약 2.89도여서
처음 두 기기를 모두 Pitch로 지정했습니다. 이후 사용자가 두 기기 모두 좌우 동작에 반응한다고
보고하여 이 축 선택은 충분히 검증되지 않았음을 인정하고 재검사를 시작했습니다.
앞뒤 동작을 손등 쪽 젖히기/손바닥 쪽 굽히기로 구체화하여 현재 장착 방향을 다시 측정합니다.
플랫폼의 P1=Z 회전, P2=X 회전 매핑은 변경하지 않습니다.

사용자가 중립 자세를 유지한 상태에서 자이로 편향 측정과 안정된 60표본 영점 보정을 실제로 완료했습니다.
두 기기 READY 및 양쪽 중립 출력 0을 확인하고 최초 동시 보정 패킷을
[calibration.json](calibration.json)에 보관했습니다.
초기 사용자 완료 응답 시에는 보정 명령이 기록되지 않아 완료로 판단하지 않았고,
중립 유지 안내 후 콘솔 보정을 실행하여 결과를 확인했습니다.
게임 내 SENSOR 버튼 클릭이 실제 중계 모드에 반영되는 것도 확인했습니다.

현재 장착 방향/영점/반전은 hardware/bridge/controllers.local.json에 저장됩니다.
이 로컬 파일은 Git에서 제외하며 매 실행의 모드는 Keyboard로 시작합니다.
착용 자세가 바뀌면 다시 영점 보정해야 합니다.

## 2026-10-27 재개: C 보정과 게임 내 검증

### 실제 장치 복구와 펌웨어 검증

사용자의 재개 요청 뒤 두 USB 장치를 다시 확인했습니다. 장치는 목록에 있지만 시리얼 표본이
오지 않던 상황은 사용자가 USB를 분리·재연결한 뒤 해소되었습니다. 원인을 전원이나 케이블
불량으로 확정하지는 않습니다. 오늘 P1 포트는 `/dev/cu.usbserial-10`, P2는
`/dev/cu.usbserial-110`으로 어제와 바뀌었지만 MAC 기반 역할은 유지되었습니다.

중단 직전 보강한 boot ID/재시작 복구와 정지 조건 자이로 편향 수집 펌웨어를 두 보드에
각각 115200으로 업로드하고 해시 검증을 완료했습니다.
근거: [P1 재개 업로드](upload-p1-2026-10-27.log), [P2 재개 업로드](upload-p2-2026-10-27.log).

실제 USB를 사용하는 [하드웨어 검사](../../hardware/bridge/hardware_check.py)는 **9개 통과, 실패 0**입니다.
두 ID 동시 수신, 실제 STOP/START, 한 기기의 표본 중단 시 해당 축만 중립 유지,
실제 보드 리셋 후 4.2초 이상 지연된 재시작 복구, 포트를 반대 순서로 다시 열어도 역할 유지 등을
검사했습니다. 이는 사람의 손목 방향이나 게임 클리어 검증과는 별개입니다.
근거: [실제 USB 검사](real-usb-2026-10-27.log).

### 빠른 현재 자세 초기화와 성공·실패 안내

사용자 요청으로 **C**를 현재 손목 자세 초기화 단축키로 추가했습니다. F5는 Godot 실행과
겹치므로 사용하지 않습니다. Python 중계가 최근의 유효한 정지 표본을 확인한 뒤 영점을 저장하고,
Godot는 요청 ID가 같은 실제 응답을 받은 경우에만 초록색 **INIT 완료**를 표시합니다.
움직임·연결 없음·저장 실패·응답 시간 초과에는 실패 안내를 표시합니다. C를 누른 상태를
유지해도 반복 요청하지 않으며, 기존 ZERO 버튼의 정밀 보정은 그대로 유지합니다.
연결된 두 역할 중 하나가 움직이면 영점 변경 전체를 취소하여 일부만 보정되는 상황을 피합니다.

별도 실제 Godot 게임 창에 네이티브 C 키를 전달하여 화면에
`INIT 완료 — P1, P2 현재 자세가 중립입니다.`가 표시되는 것을 확인했고,
같은 요청 ID의 실제 USB 중계 성공 응답과 두 기기의 READY를 확인했습니다.
이후 사용자는 Godot 편집기에서 게임을 다시 실행하여 테스트를 계속했습니다.

### 실제 착용 테스트에서 확인한 내용

- 현재 착용해 움직인 기기는 P2 `esp32-08d1f9e7279c`이며 앞뒤 플랫폼 축을 담당합니다.
- 사용자에게 앞뒤 동작으로 게임을 조작하도록 안내한 뒤 **방향이 반대**라는 응답을 받았습니다.
  P2의 `invert`만 `true`로 바꾸고 로컬 설정에 저장했습니다. P1 설정은 바꾸지 않았습니다.
- 같은 동작 재검사에서 사용자가 **“이제 방향이 맞아요”**라고 확인했습니다.
- 현재 프로필은 P1=Pitch/반전 있음, P2=Roll/반전 있음입니다. Roll/Pitch라는 센서 축 이름만으로
  손목 방향을 확정하지 않고 실제 착용 상태의 게임 반응을 근거로 수정했습니다.
- 같은 P2 컨트롤러를 계속 착용한 채 앞뒤 센서 + A/D 좌우 키보드로 공 이동과 중립 복귀를
  확인하도록 안내했고, 사용자가 **“응 잘 돼”**라고 확인했습니다. 이는 사용자의 실제 게임
  반응 확인이며, 종료한 관찰 실행의 CSV로 이 후속 플레이를 기록했다고 주장하지 않습니다.
- 반대 컨트롤러 P1의 착용 좌우 조작에서 사용자는 처음의 정상 응답을 잘못 선택했다고
  정정하고 **좌우 방향이 반대**라고 확인했습니다. 이 정정 응답을 기준으로 P1 `invert`만
  `true`로 바꾸고 저장했습니다. P2는 변경하지 않았습니다.
  반전 후 재검사에서 사용자가 **“이제 방향이 맞아요”**라고 확인했습니다.
  두 컨트롤러의 각 담당 방향 확인은 완료했습니다.
- 두 컨트롤러를 함께 착용하고 C로 보정한 뒤 P1 좌우/P2 앞뒤 동시 조작을 안내했고,
  사용자가 **“둘다 작동 돼”**라고 확인했습니다. 실제 게임에서 두 컨트롤러 동시 입력이
  작동한다는 사용자 확인을 확보했습니다. 최종 설정으로 모든 맵을 클리어했다는 의미는 아닙니다.
  LEVEL 02~04의 실제 착용 플레이 및 USB 물리 분리 중 게임 반응은 아직 확인하지 않았습니다.

전날 [실제 관찰 표본](live_game.csv)의 315.0667초에는 센서 모드, 키보드 이벤트 0인 상태에서
LEVEL 01 Goal/Mission Success가 기록되어 있습니다. 공의 좌표·속도를 직접 수정하지 않았습니다.
다만 최종 방향 수정 이전의 플레이이므로 최종 설정으로 클리어를 재검증했다고 보고하지 않습니다.
