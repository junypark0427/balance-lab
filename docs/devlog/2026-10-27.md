## 날짜 근거와 상태

**Asia/Seoul(KST, UTC+09:00)** 기준입니다. 날짜가 명시된 센서 검증·ICE 수정·QA 보고서,
실행 로그와 이날 사용자의 실제 조작 확인 대화를 근거로 보충했습니다.
파일 수정 시각만으로 개발일을 결정하지 않았습니다. 이 기록의 작성 시점에는 센서·ICE 변경이
아직 미커밋이며, 최종 확인 후 저장소에 저장하는 단계입니다. 날짜 없는 초기 제작 과정은 UNDATED에 남깁니다.

## 개발 목표

전날 남긴 펌웨어 재시작 복구와 실제 착용 방향 확인을 마무리하고,
사용자가 쉽게 중립을 보정할 수 있도록 합니다. 별도로 초고난도 ICE MODE를 추가하고
사용자 개입 없는 QA에서 일반 모드와 새 모드의 실제 동작·한계를 구분해 확인합니다.

## 구현 내용과 사용 기술

### 1. 보강 펌웨어 업로드와 역할 유지

전날 중단 때 미업로드였던 boot ID·재시작 복구·정지 조건 편향 수집 펌웨어를 두 ESP32에 각각 업로드하고
데이터 해시 검증을 완료했습니다. 두 보드에서 확인한 I²C는 모두 SDA GPIO21/SCL GPIO22입니다.
원래 요청에 있던 D2/D3를 임의 GPIO로 바꾸지 않았습니다.

포트 번호가 전날과 바뀌어도 MAC ID 역할은 유지됐습니다. 실제 USB 검사 9개가 통과했고,
한쪽 STOP/START와 실제 보드 리셋·지연 START·반대 순서 포트 재개방을 확인했습니다.
이 자동 검사는 손목 방향이나 물리 USB 분리 중 플레이 검증을 대신하지 않습니다.

### 2. C키 현재 자세 INIT과 완료 표시

정밀 ZERO는 자세를 유지하며 편향·영점을 모으는 기능입니다. 사용자가 더 간단한 초기화를 요청해
최근 최대 0.4초의 정지 표본을 확인하고 현재 자세를 영점으로 저장하는 **C키 INIT**을 추가했습니다.
실행 단축키와 겹치는 F5 대신 C를 사용합니다.

연결된 역할 중 한 기기가 움직이면 전체 영점 변경을 취소하고 실패를 표시합니다.
Godot는 키를 누른 사실만으로 성공을 표시하지 않고 요청 ID가 일치하는 중계 응답을 받은 뒤
`INIT 완료`를 표시합니다. 실제 게임 창의 C 입력과 실제 두 USB 장치 응답·초록 완료 안내를 확인했습니다.

### 3. 실제 착용 방향·반전과 동시 조작

P1은 `esp32-680947606060`의 Pitch, P2는 `esp32-08d1f9e7279c`의 Roll을 사용합니다.
처음 P2의 방향이 반대라는 사용자 응답에 따라 P2를 반전했고, 재시험에서 방향이 맞는다고 확인했습니다.
P1도 처음의 정상 선택을 사용자가 잘못 눌렀다고 정정하여 반전했습니다.
최종 설정은 **두 역할 모두 반전 ON**, P1 좌우·P2 앞뒤입니다.

사용자는 P2 센서와 A/D를 조합한 공 이동·중립 복귀, P1 방향 재검사,
이후 두 컨트롤러 동시 조작에서 각각 정상 작동을 확인했습니다.
이것은 실제 사용자 확인이며 모든 맵을 센서로 완주했다는 의미는 아닙니다.
축 이름을 손목 방향으로 단정하는 대신 장착 상태의 실제 게임 반응을 근거로 설정했습니다.

### 4. 메뉴와 ICE MODE

GAME START가 기존 레벨 선택 화면을 열도록 바꾸고 홈의 중복 LEVEL SELECT 버튼을 제거했습니다.
SETTINGS에는 기본 OFF인 ICE MODE를 추가하고 ConfigFile의 `gameplay/ice_mode`로 저장합니다.
새 레벨의 Main이 시작할 때 설정을 복사하므로 진행 중 물리를 갑자기 바꾸지 않고 다음 시작·재시작에 반영합니다.

ICE는 공·플랫폼 재질을 복제해 마찰 0.02, Linear Damp 0.012, Angular Damp 0.025와 Replace 모드를 적용합니다.
공의 속도를 직접 올리거나 좌표를 쓰는 방식이 아닙니다. Bounce·중력·CCD·충돌 형태와 최대 ±15도는 유지합니다.
OFF에서는 기존 재질·감쇠를 사용하며, 새 얼음 바닥 셰이더와 차가운 재질 보정은 ICE에만 적용합니다.

## 발생한 문제와 해결 과정

### 무인 QA에서 발견한 셰이더·표시 순서 오류

사용자가 잠든 동안 QA는 기존 코드를 고치지 않고 진행했습니다.
일반 모드 검사 246개가 통과했고 기존 진단 패널 겹침 한 항목은 계속 실패했습니다.
ICE 설정·물리 단언 84개는 통과했지만 실제 렌더링에서 `CLEARCOAT_GLOSS` 식별자 오류가 발생했습니다.
프로세스 종료 코드나 재질 할당만으로 시각 효과가 성공했다고 판단하지 않았습니다.

이후 사용자가 ICE 문제 수정을 별도로 요청했습니다. 셰이더를 Godot 4.7의
`CLEARCOAT_ROUGHNESS=0.2`로 바꾸고, 늦게 추가되는 ICE 안내 Label을 HUD의 첫 자식으로 옮겼습니다.
이로써 문구가 일시정지·성공 가림막 위에 남는 문제도 해결했습니다.
실제 Metal 픽셀 검사와 네 레벨 렌더링, 24개 headless·25개 Metal 회귀 및 기존 84개 단언을 재통과했습니다.
기존 게임 파일 중 이 수정에서 바꾼 것은 셰이더와 ICE 적용 스크립트 두 개뿐입니다.

### 재연결 후 보드·모드·보정 상태를 나누어 진단

사용자가 전원 LED는 켜졌지만 미연결로 표시된다고 보고했습니다. 처음에는 중계 프로세스가 꺼져 있어 재실행했습니다.
P2는 회복했지만 P1은 USB 어댑터만 열거되고 원시 시리얼 0바이트·칩 조회 무응답이었습니다.
USB 재연결과 소프트웨어 재시작으로는 회복되지 않았고, 사용자가 EN/RST를 누른 뒤 두 장치의 정상 측정이 돌아왔습니다.
정확한 전기적·부팅 원인은 확정하지 않으며 펌웨어를 재업로드해 덮지 않았습니다.

값은 보이는데 플랫폼이 움직이지 않던 다음 상황에서는 KEYBOARD 모드를 확인하고 SENSOR로 전환했습니다.
이후 멈춤에서는 두 장치가 수신 중이지만 정밀 보정 시작 후 `calibrated=false`여서 입력이 0인 상태를 확인했습니다.
사용자가 C로 INIT을 완료한 뒤 다시 작동한다고 확인했습니다.
연결 여부·원시 값·입력 모드·보정 완료는 서로 다른 조건입니다.

반대 기울기의 방향 반전은 ICE 약 2초였습니다. 이는 실제 Jolt 측정이지만 미로 전체 난이도의 증거는 아닙니다.
EXE·Windows Export·배포 패키징은 진행하지 않았습니다. Git Push의 실제 결과는 이후 Git 기록으로 확인해야 합니다.

최종 확인에서는 센서 자동 검사가 두 번째 C 요청의 UDP 도착 전에 결과를 읽는 간헐 실패도 확인했습니다.
게임 코드 대신 검사에 최대 0.5초의 실제 패킷 수신 대기를 추가했고 일반·빠른 headless 재실행에서 각각 45개를 통과했습니다.

## 기술적으로 배운 점

전원 LED는 MCU의 정상 부팅이나 시리얼 프로토콜·게임 입력이 작동한다는 증거가 아닙니다.
또한 유효한 센서 값이 있어도 모드·보정 게이트 때문에 실제 축은 0일 수 있으므로 상태를 단계별로 확인해야 합니다.
물리 검사를 통과해도 셰이더 API 오류는 남을 수 있어 실제 렌더링 검사가 필요합니다.
서로 다른 좌표계·축 이름을 추정하는 것보다 짧은 실제 착용 동작과 사용자의 정정 응답을 근거로 삼는 것이 정확했습니다.
