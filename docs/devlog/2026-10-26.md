## 구현 내용과 사용 기술

### 1. LEVEL 04 원본 식별과 맵 구성

실제 원본은 10월 23일 커밋 `381252f`의 `prototypes/tinkercad/Grand Duup.zip`입니다.
ZIP 안 파일은 `tinker.obj`, `obj.mtl`이며, 요청에서 제시한 괄호 포함 파일명과 달랐습니다.
압축의 원래 파일명대로 같은 시제품 폴더에 추출한 파일을 사용합니다.
OBJ의 `mtllib obj.mtl`과 실제 MTL이 일치하므로 이름을 억지로 바꾸거나 LEVEL 03 모델을 덮어쓰지 않았습니다.

실제 원본 크기는 **183.2609×280×24.5**입니다. 균일 배율 0.1과 Z-up → Y-up 변환을 사용하며
평면 중심을 플랫폼의 회전 원점에 맞춥니다. 원본 삼각형 1,460개, 분리 솔리드 17개를 유지합니다.
바닥은 **18.4×0.4×29.2**, 외곽 표시 벽 높이 1.1·두께 0.4, 외곽 충돌 높이 3.5입니다.
바닥과 벽·장애물은 같은 `AnimatableBody3D` 아래에 있어 함께 기울어집니다.

LEVEL 04의 공 반지름은 0.55로 설정했습니다. 이는 모델 단위 반지름 5.5에 해당하며
기존 LEVEL 01~03의 반지름 0.5를 바꾸지 않습니다.
ㄷ자 시작 벽 출구 폭은 1.4, 공 지름은 1.1이어서 약 0.3의 여유가 있습니다.
좁은 안쪽 원호 개구는 약 2.0005, 공 지름을 제외하면 약 0.9005입니다.
이 기하학적 여유와 실제 물리 통과 결과는 별도로 검사했습니다.

### 2. 중앙 원형 통로의 충돌체

중앙 `obj_7`은 원호 7개와 중앙 원기둥 1개로 분리됩니다.
볼록한 솔리드는 실제 꼭짓점의 `ConvexPolygonShape3D`를 사용합니다.
오목한 원호는 원본 윗면 삼각형에서 시작해, 합친 영역이 여전히 볼록하고 면적 합이 보존될 때만 병합합니다.
그 조각을 실제 높이로 압출하므로 안쪽 빈 공간과 통로를 큰 Convex 하나로 막지 않습니다.

원호 7개에는 **68개 Convex**, 전체 모델에는 **78개 프록시**가 있습니다.
원형 구조에 임의 회전 기능을 넣지 않았고 Concave/Trimesh나 수평 천장도 추가하지 않았습니다.
ㄷ자 벽 모서리의 숨은 중복 부피는 충돌체에서만 정리하여 외형·개구부를 유지합니다.

### 3. 기존 게임 기능과 최종 단계 연결

공 Friction=0.24, Bounce=0.22, Linear Damp=0.05, Angular Damp=0.1, CCD를 유지합니다.
플랫폼 마찰은 0.32이며 LEVEL 04에만 회전 속도 제한 5°/초를 사용합니다. 최대 각도는 기존 ±15도입니다.
공통 입력·공·추적 카메라·미션 판정을 재사용하고, 카메라는 높이 13·거리 9·시야 14로 맞췄습니다.

시작/복귀점은 파란 원판 기준 `(-0.021015, 1.25, 13)`, Goal은 초록 원판 기준
`(-0.021015, 0.9, -13)`입니다. LEVEL SELECT에 04 카드를 연결하고 완료 시 기존 성공 패널에
`FINAL EXPERIMENT COMPLETE`를 표시합니다. RETRY와 LOBBY를 유지하며 LEVEL 05나 신규 엔딩 Scene은 만들지 않았습니다.

### 4. Pro Micro 초기 시험과 전압 검토

별도 `hardware/`에는 ATmega32U4 Pro Micro 5V/16MHz용 보드 단독·MPU6050 스케치와 보고서가 있습니다.
USB는 Arduino Leonardo로 열거되었고, `SparkFun:avr:promicro:cpu=16MHzatmega32U4` 변형에서
SDA=2, SCL=3을 확인했습니다. 이것은 **해당 AVR 보드의 매핑**이며 ESP32의 GPIO2/3이라는 뜻이 아닙니다.

MPU6050의 저전압 I²C와 5V 보드 사이의 호환성은 구매 설명만으로 확정하지 않았습니다.
전원 레귤레이터가 있다는 사실과 SDA/SCL이 5V를 허용한다는 사실도 구분했습니다.
보고서의 초기 검사에서는 센서 안전성이 확인되지 않아 센서 구동을 진행하지 않았습니다.
두 스케치의 컴파일과 이후 실제 USB에서 `START` 대기 문자열을 받는 것까지만 확인했으며,
Pro Micro에서 센서 측정이 성공했다고 기록하지 않습니다.

도구 조사 중 `arduino-cli`가 PATH에 없어 Arduino IDE 내장 CLI를 사용했습니다.
설치된 Wire 헤더에는 필요한 timeout 메서드가 있지만 `WIRE_HAS_TIMEOUT` 검사 매크로가 없어
처음 컴파일이 실패했습니다. 잘못된 매크로 조건을 제거하고 실제 timeout 호출은 유지해 다시 컴파일했습니다.
이 과정은 당시 [하드웨어 시험 보고서](../../hardware/TEST_REPORT.md)에 남아 있습니다.

### 5. 실제 연결한 ESP32 두 대 확인과 펌웨어

이후 게임용 연동에서 사용자가 보드를 ESP32 계열로 설명했고, 실제 연결한 두 장치는
모두 **ESP32-D0WD-V3 revision 3.1**로 식별됐습니다. 칩 정보로 개발보드 PCB의 정확한 제품명까지
확정한 것은 아닙니다. 기존 AVR 기록을 현재 두 ESP32의 실측 결과로 취급하지 않습니다.

요청에는 컨트롤러별 D2/D3와 GPIO21/22라는 서로 다른 배선 설명이 있었지만,
두 장치에서 실제로 실행되던 성공 펌웨어는 모두 다음을 출력했습니다.

```text
ESP32 MPU6050 quick test | SDA=21 SCL=22
Probe 0x68: status=0
WHO_AM_I: 0x68
MPU6050 FOUND: 0x68
```

따라서 **현재 두 ESP32의 검증한 I²C는 모두 GPIO21/22**입니다.
서로 다른 핀을 사용한다고 문서에 맞춰 만들어내거나 D2/D3를 GPIO 번호로 추정하지 않았습니다.
어느 시점에 이전 배선 설명과 달라졌는지는 [날짜 미확인 기록](UNDATED.md)에 남깁니다.

게임용 펌웨어는 가속도·자이로 읽기, 상보 필터 Roll/Pitch, MAC 기반 장치 ID, 오류 감지,
115200 baud의 줄 단위 JSON 송신을 구현합니다. 약 50Hz 표본, MPU6050 ±2g/±250°/s와 DLPF를 사용하며
I²C 오류를 정상 각도로 포장하지 않습니다. 첫 버전을 두 보드에 각각 업로드하고 해시 검증했습니다.
원래 시험 스케치는 보존했습니다.

### 6. USB Serial → Python → Godot

구조는 `컨트롤러 2개 → USB Serial → Python/pySerial → localhost UDP → SensorHub → TiltInput → Platform`입니다.
공의 위치나 속도를 직접 바꾸지 않고 기존 플랫폼 회전 입력에 정규화된 아날로그 값을 전달합니다.

- 각 USB 포트는 독립적으로 읽고, 포트 번호 대신 MAC 기반 ID를 P1/P2 역할에 연결합니다.
- 데드존·축 선택·방향 반전·필터·영점을 로컬 설정으로 보존합니다.
- 센서 표본이 250ms 이상 오래되면 해당 축을 0으로, Godot의 UDP가 300ms 이상 끊기면 센서 축 전체를 0으로 만듭니다.
- 센서 모드에서도 A/D와 ↑/↓가 해당 축에서 우선하며 키보드 전용 모드도 남깁니다.
- F4 운영 패널에서 등록·보정, F8에서 모드 전환을 지원합니다.

`hardware/.gitignore`는 가상환경과 로컬 역할·영점 설정을 제외합니다.
macOS 실행 스크립트와 Windows 개발용 `.bat`를 추가했지만 Windows 실기기 실행이나 EXE 패키징은 검증하지 않았습니다.

## 발생한 문제와 해결 과정

### 센서 축 이름과 실제 손목 방향이 다름

첫 측정의 각도 변화량만 보고 두 기기에 Pitch를 지정했으나 사용자가 두 기기 모두 좌우에 반응한다고 보고했습니다.
센서의 로컬 축과 손목에 붙인 방향이 같다는 가정은 충분하지 않았습니다.

최종 착용 방향과 반전은 다음 날 실제 게임에서 확인합니다.

### 긴 중립 보정 안내와 완료 확인의 혼선

중립 자세 유지 응답만으로 보정 완료를 판단하지 않고 실제 중계 명령과 안정 표본, READY를 확인했습니다.
이날 정밀 보정은 자이로 편향과 60개의 안정된 각도 표본을 사용합니다.
사용자가 오래 자세를 유지해야 하는 불편은 다음 날 C키 빠른 INIT 요청으로 이어집니다.

### 센서 재시작 후 순번 복구

중단 직전 P1 데이터 중단을 관찰했습니다. 직접 HELLO/START를 보낸 뒤 정상 표본을 다시 받았지만
그 중단 원인을 단정하지 않았습니다. 별개로 코드에서 부팅 후 3초 이내에만 순번을 복구하는 약점을 확인했습니다.
부팅별 boot ID와 정지 조건 편향 수집을 보강했고 Python 검사 11개가 통과했습니다.
**이 보강 소스는 이날 중단 시점에는 두 보드에 아직 업로드하지 않았습니다.** 다음 날 업로드 결과와 구분합니다.

### 센서

실제 두 USB 센서 수신과 LEVEL 01의 아날로그 두 축, ±15도 플랫폼 회전, 실제 공 이동을 관찰했습니다.
관찰 스크립트는 입력이나 공 상태를 쓰지 않습니다. 저장된 `live_game.csv`의 315.0667초에는
센서 모드·키보드 이벤트 0인 Goal/Mission Success가 있습니다.
다만 최종 방향 교정 이전의 플레이이므로 최종 착용 조작감 검증으로 일반화하지 않습니다.

당시 Godot 합성 UDP + 4개 레벨 실제 물리 검사 35개가 통과했습니다.
합성 입력 검사는 실제 손목 두 대의 모든 레벨 클리어와 다릅니다.
사용자 요청으로 작업을 중단하고 브리지·관찰 게임을 종료했으며, 보강 펌웨어 업로드와 최종 방향 확인을 남겼습니다.

## 기술적으로 배운 점

구멍이나 원형 통로가 있는 구조에는 하나의 큰 Convex가 원본 기능을 없앨 수 있습니다.
원본 면적을 보존하는 분할과 실제 구체 주행을 함께 사용해야 시각·충돌·플레이 가능성을 구분할 수 있습니다.

USB 시리얼 문자가 나온다는 것, MPU6050이 I²C로 응답한다는 것, 두 센서가 게임을 조작한다는 것은 서로 다른 검증 단계입니다.
또한 GPIO 번호·보드 실크 인쇄·센서 축·플레이어 역할은 별개이므로 각각 실제 근거로 확인해야 합니다.
수신 순번은 재전송 차단에 유용하지만 보드 재부팅을 식별하지 않으면 정상 표본까지 영구 거부할 수 있습니다.
