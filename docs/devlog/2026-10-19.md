## 개발 목표

두 사람이 한 키보드에서 플랫폼의 서로 다른 축을 조작하는 물리 퍼즐의 기본 구조를 만들고,
공이 움직이는 상태로 확장한 뒤 시작 화면·결과 화면과 첫 번째 미로까지 연결하는 것이 기록에서 확인되는 목표입니다.
입력과 회전 제어를 나누어 향후 센서 입력을 붙일 수 있게 하고, 기존 기능을 단계별로 검증하는 방향을 택했습니다.

## 구현 내용과 사용 기술

### 1. 최초 스냅샷: 8×8 플랫폼과 기울기 테스트

`4ff61fc`(16:54:12)의 Main은 `Node3D` 아래에 TiltInput, Platform, Ball, Camera3D, 조명,
WorldEnvironment와 HUD를 둡니다. 플랫폼은 8×0.4×8 BoxMesh/BoxShape3D이며,
공은 반지름 0.35의 SphereMesh/SphereShape3D를 가진 RigidBody3D입니다.
이때 공은 `freeze=true`로 고정되어 있어, 움직이는 공과 플랫폼 입력 문제를 분리해 확인할 수 있습니다.

플랫폼은 `AnimatableBody3D`를 사용합니다. 표시 메시와 충돌 도형을 같은 물리 몸체에 두어 회전 기준을 맞춥니다.
카메라는 `(0, 11, 9)`에 배치하고 `look_at(플랫폼 중심, Vector3.UP)`으로 방향을 정한 후
`make_current()`로 활성화합니다. “하늘을 보는 카메라”가 수정되기 전 버전은 Git에 남아 있지 않습니다.

[입력 어댑터](../../scripts/tilt_input.gd)는 `Input.get_axis()`로 A/D와 ↑/↓를 독립적으로 읽어 Vector2를 전달합니다.
[플랫폼 제어기](../../scripts/platform_controller.gd)는 키를 직접 읽지 않고 그 Vector2만 받습니다.
P1은 Z 회전, P2는 X 회전에 연결하며, 양축 동시 입력과 반대 키 상쇄를 지원합니다.
키보드 위치 기준 `physical_keycode`를 Input Map에 등록했습니다.

회전은 `_physics_process()`에서 `1 - exp(-tilt_response * delta)`를 보간 비율로 사용합니다.
입력이 없으면 목표각이 0이 되어 서서히 수평으로 돌아오고 각 축은 기본 ±15도로 제한됩니다.
별도 `_tilt` 변수에 각도를 저장하므로, 물리 몸체의 변환 동기화와 제어기의 각도 상태를 구분할 수 있습니다.
센서용 `set_sensor_axes()` 인터페이스는 있지만 센서 통신까지 구현한 것은 아닙니다.

### 2. 공 물리 활성화와 16×16 확장

`6ec09c3`(17:06:02)는 실제 Scene에서 Freeze를 해제하고 `gravity_scale=1.0`, CCD를 유지합니다.
공 반지름을 0.5, 플랫폼을 16×0.4×16으로 확장하고 Goal의 메시/감지 영역도 키웁니다.
카메라는 `(0, 22, 18)`, 직교 크기 30, 수직 오프셋 -3으로 바뀌어 큰 플랫폼과 진단 표시를 담습니다.
공에는 줄무늬 GradientTexture2D를 추가해 회전 여부를 눈으로 식별할 수 있게 했습니다.

초기 공 PhysicsMaterial은 Friction=0.6, Bounce=0.05입니다.
Linear Damp=0.05, Angular Damp=0.1을 유지합니다. 마찰은 접촉면에서의 운동에,
감쇠는 공의 선속도·각속도 감소에 관여하므로 서로 같은 설정으로 취급하지 않았습니다.
이날 반발력을 크게 올린 변경은 없습니다. 이후 LEVEL 02의 조정과 구분해야 합니다.

낙하 기준은 Y=-4에서 -6으로 낮아집니다. 16×16 판을 기울였을 때 바닥 아래로 충분히 떨어진 뒤 실패시키기 위한 변경입니다.
[ball.gd](../../scripts/ball.gd)는 낙하 사실을 `fell` 신호로 알리고,
[main.gd](../../scripts/main.gd)는 실패 횟수를 늘린 뒤 `request_reset()`을 요청합니다.
복귀는 `_integrate_forces(state)`에서 Transform3D의 Basis를 초기화하고 선속도·각속도를 모두 0으로 만듭니다.
시작점을 `platform.to_global()`로 변환하여 기울어진 플랫폼 기준 복귀도 처리합니다.
R키 공 초기화는 낙하 횟수를 증가시키지 않습니다.

### 3. 시작 화면, HUD와 Scene 전환

`c2f91ce`(17:43:02)에서 프로젝트 시작 Scene이 `main.tscn`에서 `menu.tscn`으로 바뀝니다.
실험실 배경은 기본 3D 도형과 금속·유리·네온 재질로 만들고,
메뉴는 실제 Button/CheckButton/Label/Container를 사용합니다. 참고 PNG 위에 가짜 버튼을 겹치는 방식이 아닙니다.

제목 BALANCE LAB과 슬로건, GAME START / LEVEL SELECT / SETTINGS를 연결했습니다.
버튼은 Tween으로 호버 밝기와 눌림 크기를 보간합니다.
당시 레벨 목록에는 LEVEL 01만 실제 경로가 있고 02·03은 잠금 상태입니다.

[Session](../../scripts/session.gd) Autoload가 레벨 목록, 선택 상태, 사용자 설정과 화면 전환을 담당합니다.
진단 표시·모션 줄이기·별도 창 전체 화면 설정은 실제 동작하며 `ConfigFile`로 저장합니다.
미구현 음량 설정은 넣지 않고, 내장 실행에서 지원하지 않는 전체 화면 스위치는 비활성화합니다.
전환 중 중복 요청을 막고 페이드 후 Scene을 교체하며 일시정지를 해제합니다.

HUD에는 레벨·시간·상태와 두 사람의 조작 안내를 표시합니다.
ESC는 SceneTree를 멈추고, 일시정지 UI는 `PROCESS_MODE_ALWAYS`로 계속 동작합니다.
RESUME, 전체 Scene RESTART, MAIN MENU를 분리했습니다. R은 공만 초기화하는 기능으로 남습니다.
디자인 해상도 1920×1080, 최초 창 1280×720, 최소 960×540과 Anchor/Container를 설정했습니다.
**이 커밋 시점**에는 `window/stretch/aspect="keep"`도 있습니다. 현재 미커밋 설정과는 다릅니다.

`prototypes/tinkercad/README.md`도 같은 커밋에 추가되어 시제품 보관 목적과 향후 완성 모델 관리 방침을 설명합니다.
`assets/maps/`는 미래 계획이지 이날 완성 맵이 이미 들어간 폴더가 아닙니다.

## 발생한 문제와 해결 과정

- **실제 키보드가 안 먹는 문제:** 최초 커밋 README에는 `Events=0`에서 편집기 게임 화면의 Input 모드를
  선택한 뒤 Events와 P1/P2·X/Z 값이 변했다는 사용자 확인이 이미 적혀 있습니다.
  입력 매핑이나 회전 수식을 임의 변경하지 않고 수신 단계부터 관찰한 해결입니다.
  실제 진단 날짜는 [날짜 미확인 기록](UNDATED.md)에 두었습니다.
- **공이 고정된 상태에서는 물리 콜백이 오지 않는 문제:** `request_reset()`에 Freeze 전용 직접 초기화 분기를 두고,
  나중에 물리를 켰을 때 이전 초기화 요청이 남지 않도록 처리했습니다. 이 구조는 최초 커밋부터 확인됩니다.
- **양축 기울기에서 배경이 바닥을 가림:** 장식 지지대 숨김과 장식 바닥 하강은 서로 다른 조치입니다.
  `562f2c3`에서 둘 다 확인되며, 카메라만 바꾸어 덮은 문제가 아닙니다.
- **목표 안내와 완료 상태의 차이:** 메뉴 추가 직후에는 Goal에서 시간만 멈추고 공 물리는 계속됐습니다.
  다음 성공 시스템 커밋에서 공·플랫폼 잠금과 재시도 흐름까지 연결했습니다.

## 배운 점

입력 수신, 정규화된 축, 플랫폼이 받은 값, 실제 회전을 순서대로 관찰하면 문제의 단계를 좁힐 수 있습니다.
자동 이벤트 성공과 OS 키 전달 성공은 별개입니다.
물리 사실을 알리는 공과 게임 상태를 결정하는 Main을 분리하면 실패 횟수·UI를 바꾸어도 물리 복귀 코드를 재사용할 수 있습니다.
또한 3D 장식 메시에는 충돌이 없어도 시야를 가릴 수 있으므로, 물리 문제와 표시 문제를 따로 검사해야 합니다.
