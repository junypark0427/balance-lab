# 2026-10-23 — LEVEL 03 특수 장애물과 실제 물리 주행 검증

[전체 연혁](README.md) · [이전: 10월 20일](2026-10-20.md) · [날짜 미확인 작업](UNDATED.md)

## 날짜 근거와 상태

이 기록은 날짜가 적힌 [기존 LEVEL 03 보고서](../../reports/level_03/validation.md), 실제 파일,
저장된 로그·CSV 및 2026-10-23의 작업 폴더 관찰에 근거합니다. **LEVEL 03은 아직 미커밋입니다.**
이 날짜는 구현·검증 상태를 확인하는 기준일이며, 원본 모델 제작일이나 전체 코드의 최초 작성일을 확정하지 않습니다.
Git 기준 HEAD는 `b04d4ff`(10월 20일)입니다. 실행 보고서의 환경은 Godot 4.7.2 / Jolt / macOS / Metal Forward+입니다.
아래 최초 구현의 결과와 같은 날짜의 **후속 목표 표시·난이도 수정**은 마지막 절에서 구분합니다.

## 개발 목표

Tinkercad에서 의도적으로 배치한 곡면, 급경사 피라미드, 벽 아래 통과구를 보존하면서 LEVEL 03을 연결하고,
프로젝트 로드 성공을 넘어서 실제 RigidBody3D가 시작점에서 Goal까지 이동하는지 검사하는 것입니다.
기존 입력·UI·성공 판정을 재사용하고 LEVEL 01·02의 물리 설정을 유지하는 것을 우선했습니다.

## 구현 내용과 사용 기술

### 1. 실제 원본과 좌표계 분석

요청에 적힌 `tinker(1).obj`가 아니라 실제 파일 이름은 [tinker.obj](<../../prototypes/tinkercad/3rd map/Amazing Densor-Uusam/tinker.obj>)입니다.
OBJ의 `mtllib obj.mtl`은 같은 폴더의 [MTL](<../../prototypes/tinkercad/3rd map/Amazing Densor-Uusam/obj.mtl>)과 일치합니다.
OBJ/MTL 내용은 원본 ZIP 안 파일과 바이트 단위로 일치하며 원본을 이동·수정하지 않았습니다.

원본 범위는 X=-100..101, Y=-393..398, Z=-3..58로 실제 크기 201×791×61입니다.
21개 오브젝트와 2,076개 원본 삼각형을 유지합니다. 주황색 두 도형에는 각각 면적 0인 삼각형 96개가 있습니다.
이 192개는 앞뒤 방향을 판정할 수 없지만 부피나 Convex 충돌 윤곽에는 영향을 주지 않으므로 보존했습니다.
정상 면만 대상으로 앞면 방향을 검증했습니다.

균일 배율 0.1, Z-up에서 Y-up으로의 방향 변환, 평면 중심 (0.5,2.5) 보정으로 직사각형 비율을 유지합니다.
바닥은 여유 폭을 더한 22.1×81.1, 두께 0.4입니다.
초록색 목표 원본만 Z=-3..0으로 내려가 있어, 전체 최저점이 아니라 장애물의 공통 하단 Z=0을 바닥 상면 Y=0.2에 맞춥니다.
그렇지 않으면 나머지 벽 하단이 0.3 떠서 의도치 않은 틈이 생길 수 있습니다.

### 2. 장애물별 충돌과 기믹 보존

[LEVEL 03 빌더](../../scripts/maps/level_03_platform.gd)는 LEVEL 02 빌더를 상속하되 원본 OBJ 오브젝트와 MTL Kd 색을 읽습니다.
주황색은 일정 높이의 타원 기둥 두 개이고, 보라색은 실제 경사면이 있는 돔입니다.
색상만 보고 주황색 도형을 경사로로 가정하지 않았습니다.

| 구조 | 구현 방식 |
| --- | --- |
| 직선·대각선 빨간 벽 8개 | 실제 꼭짓점의 Convex, 방향과 두께 유지 |
| 주황색 타원 기둥 2개 | 원래 곡면 분할을 따른 Convex |
| 보라색 돔 | 7.0×7.1, 높이 4.2의 실제 꼭짓점 Convex |
| 노란 피라미드 7개 | 각 바닥 4.3×3.0, 높이 5.8, 실제 삼각 경사면 Convex |
| 통과구 벽 | 좌우 기둥 + 상단 보 3개 Convex로 분리 |
| 시작/목표 표시판 | 원본 표시판 형태의 충돌 |

통과구 외 솔리드가 볼록하다는 것을 삼각형 평면과 꼭짓점의 상대 위치로 검사했습니다.
하나의 Convex로 오목한 통과구 벽을 감싸면 빈 공간까지 채워지므로, 이 벽만 세 조각으로 나눕니다.
폭 2.2006, 높이 1.9003의 개구부와 약 0.0997 두께의 상단 보를 유지합니다.
공 지름은 1.0이며, 실제 물리 주행에서도 이 개구부를 지나갑니다.

모델 충돌체 총 23개는 같은 플랫폼 몸체의 직접 자식입니다. 수평 천장과 내부 수직 연장 벽을 추가하지 않았습니다.
이로써 돔·피라미드에 올라가거나 접촉하는 동작을 보이지 않는 벽으로 막지 않습니다.
외곽 네 벽은 기존 빌더를 재사용합니다.

### 3. 맵별 물리, 시작점과 카메라

공은 기존 RigidBody3D/ball.gd이며 Friction=0.24, Bounce=0.22, 감쇠 0.05/0.1, CCD를 유지합니다.
플랫폼 마찰은 0.32입니다. LEVEL 03 때문에 다른 맵의 재질을 바꾸지 않았습니다.
최대 기울기는 ±15도이며, 길이가 LEVEL 02의 약 2배인 판의 회전 속도만 축별 **4°/초**로 설정합니다.
입력 어댑터·공통 제어 코드는 기존 것을 사용합니다.

시작/복귀점은 `(-0.05,0.9,38.55)`, Goal은 `(-0.05,0.8,-38.55)`입니다.
낙하 복귀 시 위치뿐 아니라 선속도·각속도 초기화도 확인했습니다.
카메라는 기존 월드 기준 추적을 재사용하며 높이 16, 거리 11, 시야 15입니다.
전방 오프셋, 보간, 끝부분 범위 제한, 공을 가리는 구조물 반투명 처리를 유지합니다.

LEVEL SELECT의 세 번째 항목에 실제 Scene을 연결했습니다.
현재 Scene의 `level_index`를 사용하므로 직접 F6 실행과 메뉴 실행 모두 LEVEL 03으로 표시합니다.

## 발생한 문제와 해결 과정

### 원본 이동으로 LEVEL 02 참조가 끊김

작업 시작 시 예전 `Grand Fulffy/` 경로는 삭제 상태이고 동일한 원본이 `2nd map/Grand Fulffy/` 아래에 있었습니다.
원본을 되옮기거나 복사하지 않고 LEVEL 02 Scene과 관련 검사에서 참조 경로만 현재 위치에 맞췄습니다.
이동의 실제 날짜·수행 도구는 확인되지 않았습니다.

### OBJ의 앞면 방향과 렌더링

OBJ 삼각형을 그대로 SurfaceTool에 넣으면 Godot의 앞면 방향과 달라 내부 면처럼 보이거나 일부 면이 누락될 수 있습니다.
실제 렌더링에서 확인한 뒤 원본 파일을 수정하지 않고 생성 메시의 정점 순서를 Godot의 시계방향 앞면에 맞게 뒤집었습니다.
면적 0인 삼각형에는 유효한 법선이 없으므로, 법선 검사에서 정상 면과 구분하는 수정도 필요했습니다.

### 디지털 자동 제어기의 과조작

처음의 단순 눌림/해제 제어기는 첫 코너에서 과조작하여 시간 제한에 걸렸습니다.
게임 충돌체를 제거하거나 공을 옮겨 성공시키지 않고, 실제 기울기에 맞춰 키를 눌렀다 놓는 테스트 제어기로 바꿨습니다.
키 이벤트는 InputMap → 기존 TiltInput → 기존 플랫폼 제어 경로를 그대로 통과합니다.
긴 구간의 주행 시간 제한도 충분히 확보했습니다.

### 기존 진단 패널 검사 실패

기존 `tilt_smoke_test.gd`에서 “Visible diagnostic panel stays clear of platform at diagonal extremes” 한 항목이 실패했습니다.
작업 전 코드에 현재 설정을 적용한 경우와, 작업 전 원래 설정을 사용한 경우 모두 같은 실패가 재현됐습니다.
이를 LEVEL 03의 신규 회귀나 특정 설정 한 개의 원인으로 단정하지 않았습니다.
기존 카메라를 임의 수정하거나 검사를 삭제하여 통과시키지 않았습니다.

경로 탐색은 조작할 목표점을 정하는 데만 쓰고 실제 Goal의 진입 신호로 완료를 판정했습니다.
CSV에는 0.5초 간격의 위치·속도·기울기 338개 표본이 있습니다.

주황색 두 기둥의 반발, 돔과 피라미드 7개 경사면 하강, 25m/s 직선·대각선 벽 충돌은 별도의 물리 실험입니다.
실험 시작 때 공을 옆이나 위에 배치하고 일부는 초기 속도를 주므로, 이를 시작점에서 모든 장애물 정상에 올라간 증거로 쓰지 않습니다.
피라미드 경사는 약 69.7~75.5°로, ±15° 조작만으로 정상 등반이 가능하다고 확인한 것은 아닙니다.

실제 macOS 창에서는 F3·A·↑의 OS 키 전달을 확인했습니다. Events=6과 P1=-1/P2=-1 기록이 있습니다.
이것은 짧은 키 탭 전달 검사이며 사람이 키를 길게 누르며 전체 코스를 클리어한 결과가 아닙니다.
UI 결과창 분기 검사는 Goal에 공을 배치하는 독립 fixture를 사용하므로 연속 완주 결과와 구분합니다.

일부 제한된 headless 실행에는 사용자 로그 파일 권한·macOS 인증서 조회 메시지가 있습니다.
최종 편집기·Metal 실행 로그와 구분하며, 이런 환경 메시지를 게임 코드의 구문 오류로 기록하지 않았습니다.

## 후속 수정 — 목표 표시 깜빡임과 사각뿔 구간 난이도

### 요청과 작업 범위

개발노트 작성 중 사용자가 LEVEL 03의 초록색 도착 지점 깜빡임과 마지막 사각뿔 구간의 낮은 난이도를 보고했습니다.
문서만 작성하라는 앞선 범위에 대해 게임 수정이 별도로 요청되어, LEVEL 03 빌더와 관련 검사 두 개만 추가로 수정했습니다.
원본 OBJ/MTL, 기존 Scene 및 공통 물리·입력·카메라 코드는 변경하지 않았습니다. Commit/Push도 하지 않았습니다.

### 깜빡임 원인과 해결

원본 초록색 `obj_20`의 윗면은 플랫폼 로컬 Y=0.2로 새 바닥 상면과 일치합니다.
같은 높이의 면을 그리면 깊이 판정이 경쟁하는 z-fighting이 발생할 수 있습니다.
기존에는 이 원본 초록색 면과 별도의 GoalMarker가 모두 표시되어 있었습니다.

원본 메시/충돌 데이터는 남기고 `obj_20`의 시각 노드만 숨겼습니다.
기존 GoalMarker는 원본 표시판의 2×2 크기에 맞추고 바닥보다 위에 있는 하나의 표시로 사용합니다.
Marker 중심 Y=0.315, 두께 0.02로 면이 겹치지 않으며 불필요한 그림자도 끕니다.
목표 Area3D와 Mission Success 판정은 그대로입니다. 실제 렌더링의 목표 근접 화면도 확인했습니다.

### 난이도 조정

원래 흩어져 있던 사각뿔 7개는 각각의 크기 4.3×3.0, 높이 5.8과 경사면을 그대로 두고 배치만 바꿨습니다.
첫 줄에 4개, 두 번째 줄에 3개를 엇갈려 놓아 중앙 직진 경로를 없앴습니다.

- 첫 줄 중심 Z=-18, 좌우 중심 간격 5.25.
- 두 번째 줄은 6.2만큼 더 앞(-Z)에 놓고 좌우 간격을 1.3배로 펼칩니다.
- 첫 줄의 세 진입 틈에서 고정 X로 직진하면 두 번째 줄에 막힙니다.
  실제 구체 스윕 검사로 확인했고, 통과하려면 P1의 좌우 보정과 P2의 앞뒤 진행을 조합해야 합니다.
- 바닥에서 측정한 첫 줄의 피라미드 사이 간격은 0.95입니다. 피라미드는 위로 갈수록 좁아지므로
  이 수치만으로 구체 통과 여부를 판단하지 않고 실제 반지름 0.5 공의 물리 완주를 확인했습니다.
- Inspector의 `pyramid_slalom_enabled`로 원래 배치와 비교할 수 있습니다.
  간격·줄 사이 거리·진입 Z·두 번째 줄 펼침 비율도 조절 가능합니다.

추가 장애물이나 보이지 않는 내부 장벽은 만들지 않았습니다. 높이·공 속도를 전역으로 올리는 방식도 사용하지 않았습니다.

### 검증과 시행착오

후속 작업에서는 실제 Godot 엔진 검사를 재실행했습니다.
키 이벤트 연속 주행에서 약 156.4초에 추가 낙하 없이 Goal에 도달하고 Mission Success가 발생했습니다.
이는 자동 제어의 시간이며, 이전 자동 주행보다 짧다는 사실을 숨기거나 난이도 증가의 수치 증거로 쓰지 않습니다.
이번 조정의 기준은 단순 중앙 통과 제거와 진입·좌우 정렬 요구이며 사람 두 명의 난이도 평가는 아직 필요합니다.

첫 직선 우회 검사에서는 스윕 구체를 바닥과 접촉시킨 상태로 시작해 기대한 충돌을 검출하지 못했습니다.
실제 주행은 성공했지만 검사 하나가 실패한 상태였으며, 검사 구체를 바닥과 분리한 높이에서 시작하도록 고쳤습니다.
게임 충돌을 바꾸어 검사만 통과시킨 것은 아닙니다. 수정 후 직진 차단 검사도 통과했습니다.

기존 장애물/경사면/CCD/리셋 검사 30개와 메뉴/UI 검사 41개도 다시 통과했습니다.
물리 완주 검사에는 목표 표시 단일화·원본 크기 보존·직진 차단 검사를 추가했습니다.
검사 스크립트는 기존처럼 공을 순간이동시키지 않는 연속 주행과 별도 배치 실험을 구분합니다.

이 후속 실행의 로그는 `/tmp/balance-level03-tuning/`, 새 화면 캡처는 `/tmp/balance-level03/`에 있습니다.
기존 `reports/level_03/`는 **배치 조정 전** 검증의 역사적 증거로 보존했습니다. 임시 로그는 정리될 수 있습니다.
현재 수정 근거: [LEVEL 03 빌더](../../scripts/maps/level_03_platform.gd),
[추가 회귀 검사](../../tests/level_03_test.gd), [장애물·목표 화면 검사](../../tests/level_03_obstacle_test.gd).

### 배운 점

바닥과 표시판이 같은 높이에 있는 문제는 색상을 바꾸거나 다른 물리 재질을 쓰는 것으로 해결되지 않습니다.
시각 중복을 없애되 물리 판정은 보존할 수 있습니다.
난이도는 시간이나 속도만으로 결정되지 않으므로, 실제 통과 가능성을 유지하면서 정렬과 방향 전환 요구를 조절하고
사람의 플레이 평가를 별도로 받는 것이 필요합니다.
