## 향후 업데이트 방법

1. 작업한 날짜의 `YYYY-MM-DD.md`가 있으면 해당 문서에 추가합니다. 없으면 같은 형식으로 새 파일을 만듭니다.
2. 개발일, 커밋 시각, 검사 실행일을 구분합니다. KST가 아닌 원본 시각은 시간대를 함께 보관합니다.
3. 목표 → 실제 구현 → 문제/원인 → 해결 → 결과/한계 → 배운 점 → 근거 순서로 기록합니다.
   근거가 없는 원인이나 항목은 “미확인”으로 남깁니다.
4. 커밋 전에는 “미커밋 상태”로 적고, 이후 실제 커밋 해시를 보충합니다. 예전 개발일을 커밋일로 덮어쓰지 않습니다.
5. README 날짜별 목차에 시간순으로 링크를 추가합니다. 이미 설명한 공통 시스템은 이전 일지에 연결하고 변경점만 씁니다.
6. UNDATED 항목의 날짜를 확인하면 근거와 함께 해당 일지로 옮기고, 원래 항목에는 이동 안내를 남깁니다.
7. 검사에는 입력 방식, 엔진/환경, 실제 물리 진행 여부, 통과·실패, 재현 조건, 로그 경로를 적습니다.
   테스트 준비용 순간이동과 연속 주행을 구분하고, 민감한 환경값이나 인증 정보는 남기지 않습니다.
8. 상대 링크와 근거 파일의 존재를 확인합니다. 역사 속 경로가 삭제됐다면 코드 문자열로 기록하고 현재 경로를 따로 연결합니다.

날짜별 문서의 기본 틀은 다음과 같습니다. 자료가 없으면 소제목을 생략하거나 미확인으로 표시할 수 있습니다.


## 2차 정리 계획 — 작품 완성 후

이번 1차 문서는 중간 개발 상태의 복원본입니다. 완성 후에는 이후 일지와 최종 검증 기록을 추가하고,
미해결 표시 문제, 실제 두 사람의 플레이 결과, 맵별 난이도·클리어 시간, 센서 도입 여부를 실제 결과로 갱신합니다.
최종 기능 목록과 기술 선택의 장단점을 대조하고 프로젝트 전체에서 배운 점을 정리합니다.
**2차 정리는 아직 수행하지 않았으며, 최종 테스트 성공이나 작품 완성을 미리 기록하지 않습니다.**
